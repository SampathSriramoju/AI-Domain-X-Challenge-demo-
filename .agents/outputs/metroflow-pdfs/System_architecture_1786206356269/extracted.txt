CHAPTER 1 — SYSTEM OVERVIEW 
●​ System purpose: MetroFlow AI is an offline municipal traffic analytics and signal 
timing optimization platform designed to transform historical vehicle count data and 
road metadata into optimized, explainable, and safe signal timing plans. 
●​ Functional requirements: Ingest historical 15-minute traffic count CSVs and road 
geometry metadata, validate and sanitize input data, perform temporal cluster peak 
window detection and Volume-to-Capacity (V/C) ratio bottleneck identification, 
compute Webster-based optimal green splits and cycle lengths, run M/M/1 queuing 
"before vs. after" simulations, generate Azure OpenAI-powered plain-language 
engineering rationales, and export NEMA-compliant controller CSVs and PDF 
executive reports. 
●​ Non-functional requirements: Complete corridor optimization calculations in under 
5 seconds; return LLM narratives in under 3 seconds; maintain a queuing model 
variance within $\pm 10\%$ of Highway Capacity Manual (HCM) standards under 
stable flow; enforce TLS 1.3 encryption in transit and AES-256 at rest; achieve 99.9% 
uptime availability for the web dashboard. 
●​ Product workflow: Users authenticate via secure municipal SSO, upload traffic 
count CSVs and define intersection metadata, review automated peak congestion 
and bottleneck heatmaps, execute the offline optimization engine to adjust green 
splits, evaluate side-by-side queue and delay simulation reductions with stress-test 
sliders, inspect AI engineering narratives, and download field-ready controller files. 
●​ High-level architecture: A modular web application featuring a Streamlit/web 
dashboard frontend, a Python FastAPI backend orchestrating data validation, 
analytics, deterministic Webster optimization, safety validation, queuing simulation, 
and Azure OpenAI integration. 
●​ Design principles: Engineering credibility through zero "black box" decisions; 
extreme simplicity for a 5-minute analyst workflow; safety primacy via hardcoded 
statutory bounds; explicit simulation assumptions with zero guaranteed performance 
claims. 
●​ Assumptions: Historical counts reflect underlying demand patterns; intersections 
utilize standard NEMA phasing sequences; driver behavior adheres to baseline 
Highway Capacity Manual constants unless modified. 
●​ Constraints: Strictly offline decision support with zero direct actuation of live traffic 
controllers; all recommendations serve as advisory deliverables requiring human 
engineering sign-off.

Module Explanations 
●​ Streamlit Dashboard: The interactive web frontend providing workspace navigation, 
drag-and-drop file upload zones, GIS heatmap visualizations, optimization parameter 
controls, and export triggers. 
●​ Data Upload & Validation Module: Parses CSV files, checks timestamps and data 
types, flags missing or corrupted records, and applies anomaly filters before analysis. 
●​ Analytics Engine: Executes rolling 1-hour temporal cluster analysis, computes 
Volume-to-Capacity (V/C) ratios, and assigns Highway Capacity Manual (HCM) Level 
of Service (LOS) grades. 
●​ Signal Optimization Engine: Applies deterministic Webster formulas to calculate 
optimal cycle lengths, distribute green splits proportionally, and determine 
green-wave coordination offsets. 
●​ Safety Validator: Intercepts optimization outputs to hardcode and enforce statutory 
minimum pedestrian walk times and clearance intervals. 
●​ Simulation Engine: Utilizes M/M/1 and Webster queuing mathematics to model 
before-versus-after delay, queue dissipation, and volume-surge stress testing. 
●​ AI Explanation Module: Sends structured JSON payload summaries of simulation 
metrics to Azure OpenAI to produce transparent, plain-language engineering 
rationales without performing calculations. 
●​ Export Module: Compiles NEMA-compliant controller CSV timing sheets and 
branded executive PDF summary reports.

●​ Primary Key: count_id. 
●​ Foreign Keys: project_id references projects(project_id), intersection_id references

●​ Indexes: idx_count_lookup on (project_id, intersection_id, timestamp). 
●​ Validation Rules: volume >= 0, timestamp must follow YYYY-MM-DD HH:MM:SS 
format.

CHAPTER 6 — DATA FLOW 
●​ CSV Upload: User uploads historical 15-minute volume counts and metadata files 
via the web portal. 
●​ Validation: System ingests payloads, checking schema conformity, column headers, 
and data types. 
●​ Cleaning: Null values are interpolated from adjacent intervals, negative numbers 
floored, and extreme outliers clamped to physical saturation limits. 
●​ Analytics: Cleaned volumes are aggregated into hourly flow rates to establish 
baseline throughput. 
●​ Peak Detection: Rolling 1-hour sum clustering isolates AM, midday, and PM peak 
demand periods. 
●​ Bottleneck Detection: Approach capacities are computed using lane geometry and 
saturation flows, calculating V/C ratios and flagging intersections $>1.0$ as LOS F 
bottlenecks. 
●​ Optimization: Webster's formula calculates optimal cycle lengths and distributes 
green time proportionally to critical lane volumes. 
●​ Simulation: M/M/1 and Webster queuing formulas model before-versus-after delay 
reductions and queue dissipation. 
●​ AI Explanation: Structured JSON payloads of simulation metrics are transmitted to 
Azure OpenAI to generate plain-language engineering rationales. 
●​ Dashboard: Processed metrics, heatmaps, comparative tables, and interactive 
stress-test sliders are rendered in the Streamlit UI. 
●​ Report Export: Final NEMA CSV timing sheets and branded executive PDF reports 
are compiled and made available for download.

CHAPTER 8 — ANALYTICS ENGINE 
●​ Traffic Volume Analysis: Aggregates 15-minute interval logs into hourly flow rates to 
establish temporal volume distribution. 
●​ Peak Detection: Applies rolling 1-hour sum windows across 7-day datasets to 
identify AM, midday, and PM peak demand blocks. 
●​ LOS Calculation: Evaluates control delay per vehicle to assign Highway Capacity 
Manual Level of Service grades from A through F. 
●​ V/C Ratio: Computes demand-to-capacity ratios ($v/c$) using approach volume 
demand divided by lane count multiplied by saturation flow ($\sim 1900 \text{ 
veh/hr/lane}$) and green ratios. 
●​ Queue Estimation: Models vehicle queue accumulation based on arrival rates 
exceeding discharge capacity during peak intervals. 
●​ Delay Estimation: Calculates uniform delay ($d_1$) and random/overflow delay 
($d_2$) using Webster formulation logic. 
●​ Ranking: Orders corridor intersections in descending sequence based on absolute 
peak approach V/C ratios. 
●​ Output Objects: Returns structured JSON dictionaries containing peak start/end 
times, V/C ratio arrays, LOS grades, and ranked bottleneck node IDs. 
●​ Dependencies: NumPy, Pandas, SciPy. 
CHAPTER 9 — OPTIMIZATION ENGINE 
●​ Inputs: Critical lane volumes ($v_c$), clearance lost times ($L$), minimum 
pedestrian crossing times, and user-defined cycle bounds ($60\text{s}$ to 
$180\text{s}$). 
●​ Calculations: Determines critical flow ratios ($y = v_c / s$), sums critical ratios for 
the intersection ($Y = \sum y$), applies Webster's formula $C_0 = \frac{1.5L + 5}{1 - 
Y}$ to compute optimal cycle lengths, and allocates effective green time 
proportionally to phase demand ratios. 
●​ Outputs: Recommended cycle length, phase-by-phase green split distributions, and 
arterial coordination offset values. 
●​ Safety Constraints: Hardcodes statutory minimum pedestrian walk times and 
clearance intervals, rejecting or overriding any split calculation that breaches 
pedestrian safety minimums. 
●​ Optimization Flow: Ingest critical volumes $\rightarrow$ compute flow ratios 
$\rightarrow$ apply Webster formula $\rightarrow$ constrain within min/max bounds 
$\rightarrow$ run safety validator check $\rightarrow$ output phase allocation arrays. 
●​ Module Boundaries: The optimization engine executes strict deterministic Python 
mathematical calculations; the LLM is completely isolated from numerical 
computation to prevent hallucinations. 
CHAPTER 10 — SIMULATION ENGINE 
●​ Current Scenario: Evaluates baseline static timing plans against historical peak 
volume demands, yielding baseline control delay, queue length, and LOS grades. 

--- PAGE 11 ---
●​ Optimized Scenario: Evaluates Webster-optimized green split allocations against 
the same volume demand, computing improved control delay, shorter queue lengths, 
and enhanced LOS grades. 
●​ Metrics: Average control delay ($\text{sec/veh}$), peak queue length 
($\text{meters}$), intersection LOS grade, estimated fuel savings 
($\text{gallons/day}$), and $\text{CO}_2$ emission reductions ($\text{kg/day}$). 
●​ Assumptions: Stable, steady-state arrival patterns; standard saturation flow rate of 
$1900 \text{ veh/hr/lane}$; absence of heavy vehicle or steep grade impedance 
unless customized. 
●​ Limitations: M/M/1 and Webster queuing models assume steady-state arrivals and 
can under-predict delay during extreme oversaturated conditions ($V/C > 1.2$) 
where queues compound exponentially. 
●​ Outputs: Side-by-side comparative metric arrays, percentage reduction badges, and 
dynamic stress-test response values. 
CHAPTER 11 — AI ARCHITECTURE 
●​ Prompt Generation: Wraps structured JSON payloads of simulation before/after 
metrics into expert traffic engineering prompt templates that instruct Azure OpenAI to 
explain cause-and-effect drivers. 
●​ Structured JSON: Enforces strict JSON data schemas passed between the 
deterministic Python calculation engine and the Azure OpenAI endpoint. 
●​ Explanation Generation: Produces 2 to 3 paragraph plain-language Markdown 
narratives explaining why specific green time adjustments were made and confirming 
that pedestrian safety minimums were preserved. 
●​ Safety: Strictly prohibits the LLM from executing mathematical calculations, altering 
numerical split values, or overriding safety constraints. 
●​ Fallback Behavior: If Azure OpenAI times out or encounters rate limits, the system 
falls back to displaying a clean, deterministic template-based engineering summary. 
●​ Rate Limits: Implements exponential backoff retry logic and client-side request 
throttling to comply with Azure OpenAI token limits. 
●​ Failure Handling: Gracefully catches API errors, logs exceptions internally, and 
displays a non-blocking notification banner on the UI dashboard. 
CHAPTER 12 — SECURITY 
●​ Input Validation: Strictly validates all uploaded CSV files against required schema 
definitions, rejecting unparseable files or malicious payloads. 
●​ File Validation: Enforces MIME-type checking (text/csv) and file size limits ($\le 
25\text{MB}$) on all user uploads. 
●​ Error Handling: Implements centralized exception management to prevent raw stack 
traces and internal system details from leaking to client responses. 
●​ Secrets Management: Stores database credentials, API keys, and Azure OpenAI 
tokens securely in environment variables via .env files, omitting secrets from source 
control. 
●​ Responsible AI: Hardcodes mathematical safety limits into deterministic Python 
code to ensure AI-generated narratives cannot influence critical safety constraints.
