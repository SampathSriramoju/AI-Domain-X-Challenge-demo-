2. SYNTHETIC DATA STRATEGY 
To successfully demonstrate the MVP, the synthetic data must replicate real-world traffic 
physics and daily commuter rhythms. 
●​ Dataset Structure: A 5-intersection continuous arterial corridor (Main Street) 
cross-sected by minor side streets. 
●​ Number of Approaches: 4 approaches per intersection (N/S/E/W). 
●​ Time Resolution: 15-minute intervals. 
●​ Duration: 7 continuous days (Monday - Sunday). 
●​ Expected Congestion Pattern: 
○​ AM Peak (07:45 - 09:15): Heavy Eastbound directional flow (commuters 
heading to city center).​
 PDF 
○​ Midday (11:30 - 13:00): Balanced, moderate flow. 
○​ PM Peak (16:30 - 18:00): Heavy Westbound directional flow (commuters 
heading home). 
○​ Off-Peak: Low, stable volume. 
●​ Expected Bottleneck: 
○​ Requirement from PRD: Intersection #4 (Main St & 5th Ave) must be the 
primary bottleneck with a V/C ratio of 1.12 (LOS F).​
 PDF 
●​ Generation Strategy [Recommended Enhancement for Hackathon]: Use a 
deterministic sine-wave function layered with random Gaussian noise to generate 
base daily traffic. Multiply Eastbound AM intervals by a factor of 2.5 and Westbound 
PM intervals by 2.5. Cap the physical capacity (lanes × saturation flow) so that 
Intersection #4 mathematically triggers V/C>1.0 and initiates queue spillback in the 
simulation.

5. PEAK CONGESTION ANALYSIS 
Requirement from PRD: Identify peak congestion windows automatically using temporal 
cluster analysis (FR-B02). 
PDF 
●​ Inputs: Cleaned 15-minute interval total intersection volumes. 
●​ Calculation: 
1.​ Apply a rolling 1-hour sum window across the 24-hour timeline. 
2.​ Group by time-of-day across the 7-day dataset to find the average hourly 
volume for each 15-minute start time. 
3.​ The absolute maximum rolling sum identifies the AM Peak, Midday Peak, 
and PM Peak boundaries. 
●​ Output: Time windows (e.g., 07:45 - 08:45 AM). 
●​ Visualization: An hourly volume bar chart with shaded overlay boxes highlighting the 
identified peak periods.​
 PDF 

--- PAGE 6 ---
●​ Edge Cases: Flat volume profiles (e.g., weekends) where peaks are not distinct. The 
system will default to the highest continuous 60-minute segment. 
6. BOTTLENECK DETECTION 
Requirement from PRD & Research: Calculate V/C ratios, assign HCM LOS based on delay, 
and map multi-intersection bottlenecks. 
PDF+ 1 
●​ Capacity (c): Number of Lanes × Saturation Flow (default 1,900 veh/hr/lane under 
ideal conditions). 
●​ Traffic Demand (v): Hourly flow rate derived from the peak 15-minute volume. 
●​ V/C Ratio (X): Calculated as v/c. 
●​ Worked Synthetic Example: 
○​ Intersection 4, Eastbound Approach. 
○​ Demand (v): 2,120 veh/hr. 
○​ Lanes: 2. Saturation Flow: 1,900 veh/hr/lane. 
○​ Green Ratio (g/C): 0.45. 
○​ Capacity (c): 2×1,900×0.45=1,710 veh/hr. 
○​ V/C Ratio: 2,120/1,710=1.24. 
●​ Ranking: Intersections are ranked descending by their highest approach V/C ratio. 
V/C >1.0 is flagged as a bottleneck (LOS F).​
 PDF

10. WHAT-IF STRESS TESTING 
Requirement from PRD: Interactive slider controls allowing users to perform traffic volume 
variation stress testing (+/- 30%). 
PDF 
●​ Design: A web UI slider on the Simulation screen mapping to multipliers: [0.7, 
0.8, 0.9, 1.0, 1.1, 1.2, 1.3]. 
●​ Logic: When the user moves the slider to "+20%", the frontend passes a 1.2 
demand multiplier to the Python API. The backend recalculates the V/C ratio, Delay, 
and Queue length using the new demand over the fixed, recommended capacity. 
●​ Output: The UI updates dynamically, showing if the proposed plan fails (LOS drops 
to F) under a 20% surge, proving/disproving plan robustness.​

16. FINAL IMPLEMENTATION SPECIFICATION 
For the developer building this platform: 
1.​ "WHAT DATA DO WE NEED?" You need a continuous 7-day CSV of 15-minute 
traffic counts, tagged by intersection and approach, alongside basic road geometry 
(lanes, speed limits). Generate this synthetically using a sine-wave baseline heavily 
weighted in the Eastbound AM and Westbound PM directions.​
 PDF 
2.​ "WHAT DO WE DO WITH THAT DATA?" Validate it (remove negatives/nulls), 
aggregate it into hourly flow rates, and calculate the V/C ratio by dividing the volume 
by the approach capacity (lanes × saturation flow).​
 PDF 
3.​ "HOW DO WE CALCULATE THE RESULT?" Use deterministic Python to run 
Webster's formula C0​=(1.5L+5)/(1−Y). Distribute the resulting green time based on 
the ratio of competing critical lane volumes. Pass this through a safety check that 

--- PAGE 12 ---
hard-stops any green time below the pedestrian minimum walk time.​
 PDF+ 1 
4.​ "HOW DOES THE AI USE THE RESULT?" Do not let the AI do math. Take the 
before-and-after simulation numbers generated by your Python queuing equations, 
wrap them in a JSON, and prompt Azure OpenAI to write a 2-paragraph summary 
explaining why the splits changed.​
 PDF 
5.​ "WHAT DOES THE USER SEE?" A clean web dashboard showing a corridor 
heatmap, side-by-side delay/queue reduction metrics, a "what-if" volume slider, and 
downloadable NEMA CSV / PDF reports. Every screen must clearly label outputs as 
offline simulation estimates.​
